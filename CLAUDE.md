## Architecture

Multi-tenant SaaS REST API for feedback collection, roadmap planning, and changelog publishing. Built with Node.js/Express, MySQL (raw SQL via `mysql2/promise`), and JWT auth. No ORM.

### Layer structure

```
app.js              → Express setup, route mounting, static file serving
src/routes/         → Express routers (one file per domain)
src/main/           → Business logic handlers (called directly by routes)
src/middlewares/    → JWT auth, language validation, pagination, file upload
src/common/         → setServerResponse() response builder
src/consts/         → HTTP codes, response message keys
database/dbPool.js  → MySQL connection pool (10 connections, UTC timezone)
uploads/            → Stored user-uploaded files
```

### Request flow

`Route → authenticateToken → languageValidator → handler function → setServerResponse()`

Route handlers call business logic directly (no service layer). Handlers return promises; routes use `.then().catch()`.

### Response format

Handlers build responses with `setServerResponse(code, msgKey, lg, result?)`, which returns `{ statusCode, status: "success"|"failed", message, result }`. Routes then send `{ status, message, data: result }` to the client (note the `result` → `data` rename happens in the route).

Messages are looked up from **`src/common/response-message.json`** by key + language. It holds the **8 major EU languages** (English, German, French, Spanish, Italian, Portuguese, Dutch, Polish). **English is the source of truth — add every new key to the `en` block.** `setServerResponse` falls back **per-key to English** (`langMessages[key] || en[key] || key`), so a language that only translates part of the file is safe and untranslated keys show English. `lg` comes from the request (the frontend sends the user's selected UI language); the other language blocks currently hold a machine-translated core and can be filled out over time.

### Multi-tenancy

Every authenticated request has `req.auth = { id, email, tenantId, role }` (set by `authenticateToken` from the JWT plus a DB re-check that the user is still active). Tenant-scoped data queries filter by `tenant_id`. **Tenant roles are only `owner` and `user`** (the `users.role` enum). `owner` administers the workspace (team/role changes, billing, feedback deletion); `user` is a plain member. The platform operator (**`admin`**) is NOT a tenant role — it's a **role flag on the `users` account** (`users.is_platform_admin`), authenticated through a separate door (`/admin-login`) but the same account (see below).

**Multiple workspaces per account:** an email can have a `users` row in several tenants — each is one of that account's "workspaces". `src/main/users/workspaces.js` (routes `GET /users/workspaces`, `GET /users/workspaces/check-subdomain`, `POST /users/workspaces/create`, `POST /users/workspaces/switch`) lists them, validates subdomain availability live, creates a new tenant + owner (seeding default `planned`/`in_progress`/`completed` roadmap columns), and re-issues a JWT scoped to a chosen workspace. Login by email (unscoped) returns the first matching row, so it picks a default workspace.

**`subdomain` vs `website`:** `subdomain` is unique and required (the portal host); the **owner** can change it later from Branding settings (`updateTenant` validates format + reserved words → `400 invalid_subdomain`, and uniqueness → `409 subdomain_taken`, keeping `slug` in sync). `PUT /tenants/update/:id` is **owner-only and self-scoped** (`:id` must equal `req.auth.tenantId`, else `403`). The onboarding "Website" is the company's site — stored in the non-unique, informational `website` column. (Custom domains are **not** a feature; the `tenants.custom_domain` column is unused/legacy and never written.)

**Pending accounts / onboarding:** `users.tenant_id` is **nullable**. Registration (`registerNewUser`) creates a *pending* account with `tenant_id = NULL` and a global email-uniqueness check — it does **not** default into tenant 1. A pending account has zero workspaces (so it can't see another tenant's data); its first `createWorkspace` **claims that row** (sets `tenant_id` + `role='owner'`) rather than inserting a new one. Subsequent workspaces insert a fresh owner row.

User self-service handlers (personal data, profile/password update) key off the authenticated `req.auth.id` **only** — never a client-supplied `userId` — to prevent cross-account writes.

### Authentication

- JWT Bearer tokens (`Authorization: Bearer <token>`), 90-day expiry by default
- `authenticateToken` middleware verifies token then queries DB to confirm user is still active
- Passwords hashed with bcrypt
- Unauthenticated routes: `POST /users/login`, `POST /users/register`, `POST /tenants/create`, `POST /admin/auth/login`, and the entire `/public/*` portal API (below)
- **Platform admin auth.** "Platform admin" is a **ROLE flag on a `users` account** — **`users.is_platform_admin`** (there is no separate `admins` table anymore). The same account can act as a normal user (via `/login`) **or** as an admin (via `/admin-login`), chosen by which door it enters. `adminLogin` (`src/main/admin/adminLogin.js`) authenticates against `users` **requiring `is_platform_admin = 1`** and issues a JWT with **`scope:'admin'`** (+ `email`, `adminUserId`); **`authenticateAdmin`** (`src/middlewares/jwt/authenticateAdmin.js`) verifies that scope, then re-checks the role by **email** (`EXISTS(SELECT 1 FROM users WHERE email = ? AND is_platform_admin = 1 AND is_active = 1)` — an account shares its rows/password across workspaces) and sets `req.admin = { id, email, fullName }` (`id` is a `users.id`). All `/admin/*` routes except login sit behind it. `manageAdmins` **grants/revokes the flag** (never deletes the user account); self-guard is by email. Bootstrap with `node scripts/create-admin.js <email> <password> [name]` (grants the role to that account, creating a pending user if new); further admins are granted in-panel. Support audit columns (`support_*.sender_admin_id` / `closed_by_admin_id`) and `promo_codes`/`offers.created_by` now hold a `users.id`.
- **Password reset** (`src/main/users/passwordReset.js`, table `password_resets`, migration `scripts/add-password-resets.js`). Three **unauthenticated** routes on `userRouter`: `POST /users/password/forgot`, `GET /users/password/reset/:token`, `POST /users/password/reset`. `requestPasswordReset` **always resolves success** (no account enumeration) and only emails a link when an active `users` row matches. The emailed token is `crypto.randomBytes(32)` but the table stores only its **sha256 hash** (a DB read must not grant reset ability), keyed by **email**, single-use, 1-hour expiry; requesting a new link invalidates prior pending ones. `resetPassword` updates **all `users` rows for the email** (`WHERE email = ?` — an account's workspaces share one `password_hash`) inside a `FOR UPDATE` txn, then `revokeSessionsForEmail` so the reset logs the account out everywhere. Rate-limited in `app.js` (`expensiveActionLimiter` on `/forgot`, `authLimiter` on `/reset`). Email template: `src/common/emails/passwordResetEmail.js`.
- **Device sessions / one device at a time** (`src/common/sessions.js`, table `user_sessions`). Every user JWT carries an **`sid`** claim naming a session row; `authenticateToken` rejects a token whose session was revoked with **`401 "Session ended"`** (so a session dies immediately, without waiting for JWT expiry) and `touchSession`s it otherwise (throttled to one write/min). `optionalAuth` likewise falls back to *guest* for a revoked session.
  - Sessions are keyed by **email**, not `users.id` — one account may hold rows in several tenants, and switching workspaces must not look like a new device. Every place that mints a token therefore threads the `sid` through: `userLogin` / `oauthLogin` **start** one (via `startSession`), while `workspaces.js` (create/switch) and `invitations.js` (accept-as-existing) **carry the caller's through**.
  - `startSession` is the gate: on a plan without the **`multiDevice`** limit (Free, Pro) it refuses a second login with **`409 already_logged_in_elsewhere`** while another session is live. Business allows unlimited devices. The plan is that of the workspace being signed in to; an account with no workspace yet counts as Free.
  - **Force / takeover** — `startSession(user, req, { force })` and `userLogin` reading `userData.force`. A 409 means the password was correct, so the owner may confirm a takeover: `force` revokes **all** existing sessions for the email and logs in fresh (never blocks). This is the escape hatch so a stale session (browser closed without signing out) can't lock the owner out for the whole idle window; "one device at a time" still holds (the newest login wins, the rest die).
  - **A session idle >15 min (`IDLE_MINUTES`) is "abandoned"** and the next login takes it over, *revoking* it. Without this, closing the browser without signing out would lock the account out permanently. The takeover keeps the invariant: **at most one live session** on single-device plans.
  - **`POST /users/logout`** revokes the caller's session. The frontend must call it on sign-out (`lib/auth/end-session.ts`) — otherwise the user can't sign back in until the session goes idle. Deleting an account drops all its `user_sessions` rows.
  - A second **tab** shares the cookie, so there is no login for the backend to refuse — that's blocked client-side (`SingleTabGuard`).
- **Admin Panel API** (`src/routes/admin/adminRoute.js`, handlers in `src/main/admin/`): overview counts; workspaces (list/detail/update/**plan grant=comp**/delete, + **`POST /admin/workspaces/:id/enter`** = "Open in dashboard": mints a tenant-scoped **user** token for the admin's OWN member account in that workspace so the admin can drop into its real dashboard — `403 admin_not_member` if they have no account there; not impersonation of others, only the admin's own account, e.g. the dogfood board they own) + **post moderation across any tenant** (`GET/PUT/DELETE /admin/workspaces/:id/posts…` → list / set-status (roadmap-synced) / pin / delete — `adminPosts.js`) + **comment moderation** (`GET /…/posts/:postId/comments`, `DELETE /…/comments/:commentId` — list / delete only, a top-level delete takes its replies; admins can't edit comment text — `adminComments.js`); users across all tenants (list/update/role/reset-password/delete); admins (list/create/activate/delete, self-guarded); promo codes (list/create/revoke); offers (list/create/deactivate); **support chat** (`/admin/support/*` — `sessions?status=open|closed` queue with unread-from-user + last message, session+transcript, reply, `PUT …/close`, and `unread` inbox badge — `src/main/admin/support.js`).
- **Support chat (user ↔ admin, session-based).** Any authenticated tenant user (any role/plan) contacts the platform admin. User side: `supportRouter` at `/support` (`authenticateToken`) — `POST /support/session` (get-or-create; **one open session per user**), `/support/messages/:id/list`, `/support/messages/:id`, `/support/unread` (`src/main/support/userSupport.js`). Admin side lives on `adminRouter` (above). Two tables (`support_sessions`, `support_messages` — migration `scripts/create-support-tables.js`, mirrored in `feedboard_db.sql`). **Closing is one-way for the user:** every user-side read is scoped to `status='open'`, so a closed session returns **403** and vanishes from the widget; the **admin keeps the transcript forever** — sessions are never deleted, `user_id`/`tenant_id` are `ON DELETE SET NULL`, and the display identity (`user_email`/`user_name`) is denormalized so history survives an account/workspace deletion. `admin_last_read_at`/`user_last_read_at` drive the unread counts. No realtime infra — the clients poll.

### Public portal API

`src/routes/public/publicRoute.js` (mounted at `/public`) powers the frontend's unauthenticated per-tenant portal (`app/portal/[tenant]`). No JWT. The tenant is resolved by the `attachPublicTenant` middleware from the `:subdomain` URL param, matching `tenants.subdomain`. Handlers live in `src/main/public/`. Return only safe public fields — **no author emails**, and changelog/roadmap responses must filter to published/active rows only.

**Guest submissions:** `POST /public/:subdomain/feedback` lets anonymous visitors create posts. Guest posts have `author_id = NULL` and carry optional `submitter_name` / `submitter_email` (added to the `posts` table; `author_id` is now nullable). Any query that joins the author must `COALESCE(u.full_name, p.submitter_name, 'Anonymous') AS author_name` (and admins also get `COALESCE(u.email, p.submitter_email) AS author_email`). `submitter_email` is **never** exposed on public endpoints. Guest posts **and comments** also store an optional `guest_id` (the persistent `fb_guest_id` cookie, `posts.guest_id` / `comments.guest_id`); public create handlers persist it and public read handlers (`getPublicPostDetail`) return it, so the portal can render one guest a stable pseudonymous display identity. It's a non-PII opaque browser id, safe to expose; it's nulled when the author is a logged-in user.

**Logged-in actions on the portal:** the comment/feedback create routes use an `optionalAuth` middleware (`src/middlewares/jwt/optionalAuth.js`) — a valid Bearer token attaches `req.auth`, so the post/comment is attributed to that user (`author_id` set, no guest name); otherwise it's a guest. Public detail queries return `author_id` + `author_avatar` so the client can render the avatar and decide ownership. For an **owner "hidden" (mode 2)** comment the real name is withheld but `author_avatar` is the workspace's own `branding_logo_url` (company icon), so the "Owner" reply is branded; mode 1 keeps the owner's profile picture, and a platform admin's `author_avatar` is the app icon (see the brand-icon note under *Users, roles*). **Edit/delete** are owner-only and require login (`authenticateToken`): `PUT|DELETE /public/:subdomain/posts/:postId` and `PUT|DELETE /public/:subdomain/comments/:commentId` (`src/main/public/publicOwnerActions.js`, reject with `not_your_content` unless `author_id === req.auth.id`).

**Guest voting:** `POST /public/:subdomain/posts/:postId/vote { guestId }` toggles an anonymous upvote. The `votes` table now allows guest rows (`user_id` nullable, added `guest_id`, unique `(tenant_id, post_id, guest_id)`), so guest votes land in the same table and the existing `COUNT(*)` vote counts include them unchanged. Spam is limited to one vote per browser per post via the unique `guest_id` (a persistent client cookie).

**Voting is public-board-only — this is the *only* way to cast a vote.** Votes are a signal from a workspace's users, so a workspace's own owner/team must not vote on their feedback. `/votes` (`src/routes/vote/voteRoute.js`) is therefore **read-only**: it exposes `POST /votes/post/:postId` (`getPostVotes`) and nothing else — the authenticated `POST /votes/add` + `DELETE /votes/remove/:postId` routes and their `addVote`/`removeVote` handlers were **deleted**, since `authenticateToken` meant their only possible callers were the tenant users now barred from voting. The dashboard just displays `vote_count`. Don't re-add an authenticated vote write endpoint.

### Billing & subscriptions (Paddle active · Stripe dormant)

- **Payment provider seam.** `src/common/billingProvider.js` `getBillingProvider()` picks the active provider from **`BILLING_PROVIDER`** (default **`paddle`** — a Merchant of Record, since Stripe can't pay out to Bangladesh; `=stripe` re-selects Stripe). `src/routes/billing/billingRoute.js` dispatches each op to `stripeOps`/`paddleOps` (Stripe funcs referenced **unchanged**). **`src/main/billing/paddleBilling.js`** is the Paddle implementation (client `src/common/paddle.js`, `@paddle/paddle-node-sdk`): checkout creates a **transaction** (`transactions.create`, `customData.accountEmail`) for the client's Paddle.js overlay; `reconcile`/`fetchSubscription` sync from Paddle (the no-webhook fallback + post-checkout, keyed off `billing_accounts.paddle_customer_id/paddle_subscription_id`); plan-change preview/apply (**upgrade** = `subscriptions.update` `prorationBillingMode:'prorated_immediately'` — charges the prorated diff now, credits already-paid time; the preview's `amountDueNow` is read from `immediateTransaction.details.totals.grandTotal` — the exact tax-inclusive charge, **verified to equal the actual charge**. **Downgrade = scheduled to the end of the current paid period**: the customer keeps their current (higher) plan until period end, then the lower plan applies — **no charge, no refund**. Paddle has **no native scheduled plan change** (`scheduledChange` only does pause/cancel/resume; `prorated_next_billing_period` *rejects* interval changes), so a downgrade switches the Paddle item **now** with `prorationBillingMode:'do_not_bill'` (**verified**: no charge/refund, billing date preserved → next renewal auto-bills the lower price) while the account's in-app plan stays at the higher tier until `current_period_end` via `pending_plan/pending_interval/pending_effective_at`. **`reconcile` is pending-aware** — while `now < pending_effective_at` it refreshes only status/period/ids and keeps the higher plan; once past, it mirrors Paddle's (now-lower) plan and clears the markers. `cancelScheduledChange` switches the Paddle item back to the higher plan (`do_not_bill`) + clears the markers. **Interval-changing downgrades (yearly→monthly) are rejected** (`downgrade_interval_unsupported`) — `do_not_bill` resets the period on an interval change so a paid year can't be preserved, and Paddle can't defer it; the client hides that CTA); cancel-at-period-end (`subscriptions.cancel {effectiveFrom:'next_billing_period'}` → `scheduledChange`) + resume (`update {scheduledChange:null}`); portal (`customerPortalSessions.create`); `cancelLiveSubscription` (used by comps). `accountBilling.reconcileAccount` dispatches to Paddle when active; `cancelActiveSubscription(email)` cancels the live sub on either provider before an admin/promo comp. Webhook: **`POST /webhooks/paddle`** (`src/routes/webhooks/paddleWebhookRoute.js`, mounted in `app.js` with `express.raw` before `express.json`) → `paddle.webhooks.unmarshal` (HMAC-SHA256, `PADDLE_WEBHOOK_SECRET` `pdl_ntfset_…`). **Promo codes + offers work on Paddle** (Phase 2): `src/common/discounts.js` creates a **Paddle discount** for each — an offer → a `flat` amount-off discount (`recur:true`, `restrictTo` that plan+interval's price); a percent-off promo → a `percentage` discount (`restrictTo` the plan's prices when scoped). `admin/offers.js` + `admin/promo.js` branch on `isPaddleActive()` and store the id in `offers.paddle_discount_id` / `promo_codes.paddle_discount_id` (`scripts/add-paddle-discount-columns.js`, mirrored in `feedboard_db.sql`). `redeemPromo` returns the active provider's discount ref; `paddleBilling.createCheckout` applies it to the transaction via `discountId` (a redeemed promo wins over an active offer; the code's `applies_to_plan` is re-checked server-side → `promo_plan_mismatch`). Free-plan comp codes are unchanged (provider-agnostic comp path). **Verified in sandbox**: a $2.50-off offer and a 25%-off code both applied to the cent. `scripts/paddle-setup.js` creates the Paddle products/prices; `PADDLE_PRICE_*` + `paddlePriceIdFor`/`planByPaddlePriceId` in `plans.js`. Env: `BILLING_PROVIDER`, `PADDLE_API_KEY`, `PADDLE_ENV`, `PADDLE_WEBHOOK_SECRET`, `PADDLE_PRICE_*`. **The rest of this section describes the Stripe path (dormant but intact).**
- Tiers — **Free / Pro / Business**, each billable **monthly or yearly**, defined in **`src/consts/plans.js`** (`PLANS`, `planByPriceId`, `getPlanLimits`). Each paid plan has a monthly `priceId` (`STRIPE_PRICE_PRO`/`_BUSINESS`) **and** a `priceIdYearly` (`STRIPE_PRICE_PRO_YEARLY`/`_BUSINESS_YEARLY`); Free has none. `scripts/stripe-setup.js` creates both Prices per plan and prints the IDs. **Yearly is a genuinely cheaper price, not a coupon**: the per-month equivalent is rounded to a whole dollar (`round(monthly × (1 - YEARLY_DISCOUNT))`, `YEARLY_DISCOUNT = 0.2`) then × 12, so both stay integers → Pro $8/mo ($96/yr), Business $12/mo ($144/yr). Helpers: `priceIdFor(plan, interval)`, `planByPriceId` (matches monthly **or** yearly → plan key), `intervalByPriceId`.
- **Subscriptions are per ACCOUNT, not per workspace.** The billing source of truth is **`billing_accounts`** (keyed by `email` — the account identity), holding the Stripe customer/subscription, comp status, interval, period end, and any scheduled change. **One account pays once and its plan covers every workspace it OWNS.** The account plan is **mirrored** onto each owned `tenants.plan_name` (+ display columns) so the many readers of `tenants.plan_name` (enforcement via `getTenantPlan`, portal booleans, `getMyTenant`, seats, comment gating) are unchanged. **All billing writes go through `src/common/accountBilling.js`** (`getAccount`/`ensureAccount`/`setAccountPlan`/`mirrorAccountToTenants`/`applyAccountSubscription`/`reconcileAccount`) — `setAccountPlan(email, fields)` upserts `billing_accounts` **and** re-mirrors to all owned tenants in one transaction, so the mirror can't drift. A **new workspace inherits the owner's account plan** at creation (`createWorkspace` → `mirrorAccountToTenants`). Tenant-level `stripe_customer_id`/`stripe_subscription_id` are legacy/unused (cleared by the mirror). Migration: `scripts/migrate-billing-to-accounts.js` (idempotent) builds `billing_accounts` from existing tenants (best owned plan wins; multiple live paid subs → keep highest, cancel the rest) and mirrors. Seats/limits stay **per workspace** (each owned workspace gets the account plan's full allowance).
- **Hosted Checkout + Customer Portal.** Authenticated routes at `/billing` (`src/routes/billing/billingRoute.js`, **owner only**), all keyed by the caller's **account (`email`)**: `POST /billing/status`, `POST /billing/checkout {plan, interval?, promotionCode?}` (`interval` = `"month"` default | `"year"` → picks the right Stripe price; a `promotionCode` is applied as a `discounts` entry, else `allow_promotion_codes` lets the user type one — but an active plan **offer** auto-coupon for the checkout's interval is applied when present), `POST /billing/portal` (→ Customer Portal URL), `POST /billing/redeem {code}` (promo redemption). Handlers in `src/main/billing/`. The shared client is `src/common/stripe.js` (constructed with a placeholder key when unset so the server still boots; real calls gated by `isStripeConfigured()`).
- **In-app prorated plan change** (`src/main/billing/changePlan.js` — `POST /billing/change/preview`, `/billing/change`, `/billing/change/cancel`, owner only). We do NOT rely on the Portal's proration (a Stripe-dashboard setting). Direction = `directionOf` (rank plan free<pro<business, then month<year): **upgrade** (higher tier, or same tier month→year) OR **downgrade** (lower, or year→month). **Upgrade** = `stripe.subscriptions.update(sub, { items:[{id,price}], proration_behavior:'always_invoice', payment_behavior:'error_if_incomplete' })` → charges only the prorated **difference** now (already-paid time credited); `previewPlanChange` returns the exact `amountDueNow` from `stripe.invoices.createPreview({ subscription_details:{ items, proration_behavior:'always_invoice' } })` using the invoice **`amount_due`** (interval switches reset the cycle, so proration-line sums under-count — `amount_due` is the true charge). **Downgrade** = a **Stripe Subscription Schedule** switching at period end (keep the higher tier until then, no refund); the target is stored in `billing_accounts.pending_plan`/`pending_interval`/`pending_effective_at` (mirrored to tenants) and surfaced by `getBillingStatus`. `reconcileAccount` clears `pending_*` once the live plan matches the pending target (transition done) or the schedule is gone. `cancelScheduledChange` releases the schedule. All of these operate on the **account's** subscription (looked up in `billing_accounts` by `email`), not the tenant. Verified against Stripe **test mode** for both intervals (monthly upgrade charged $5 not $15, yearly $48, month→year preview == charged).
- **Webhook needs the raw body.** `/webhooks/stripe` is mounted in `app.js` with `express.raw({ type: "application/json" })` **before** the global `express.json` so signature verification works. `handleStripeWebhook` calls **`applyAccountSubscription`** (`src/common/accountBilling.js`) on `checkout.session.completed` / `customer.subscription.created|updated|deleted` — it resolves the **account** from `sub.metadata.accountEmail` (legacy `metadata.tenantId` → owner email, else the customer id), writes `billing_accounts` (`plan_name` via `planByPriceId`, `subscription_status`, `stripe_subscription_id`, `current_period_end`), then mirrors to owned tenants. (The old per-tenant `applySubscription.js` is legacy/unused.)
- **Reconcile-on-load (no-webhook fallback).** `getBillingStatus` calls `reconcileAccount(email)` first — it pulls the **account's** latest subscription straight from Stripe, persists it to `billing_accounts`, and mirrors to owned tenants. This keeps the plan correct after Checkout/cancellation **even when webhooks aren't delivered** (e.g. local dev without the Stripe CLI, where Stripe can't reach `localhost`). A Stripe error there is non-fatal (falls back to stored values). The webhook is still the real-time path in production. `getBillingStatus` also **reads `cancel_at_period_end` live** from the subscription (not persisted) and returns it as `cancelAtPeriodEnd`, so the Billing tab can say the plan **ends on** `current_period_end` (no further charge) rather than **renews on** it. **Reconcile skips accounts with `subscription_status='comped'`** so an admin/promo grant (which has no Stripe subscription) is never reset to free — **except** it reverts a **timed comp whose `current_period_end` has passed** back to Free (lifetime comps, `current_period_end` NULL, are preserved forever).
- **Comps & promo codes (account-level).** A **comp** is a paid `plan_name` with `subscription_status='comped'` and no Stripe subscription, held on `billing_accounts` and mirrored to owned tenants. **Admin grant** (`src/main/admin/accounts.js` `setAccountPlanAdmin(email, plan, durationMonths, lg)` → `PUT /admin/accounts/:email/plan {plan, durationMonths}`) comps/reverts the **whole account**: falsy/0 `durationMonths` = **lifetime** (`current_period_end` NULL), a positive integer = expires after N months (reverted to Free by `reconcileAccount` once past). It **cancels any live account Stripe subscription first** so the override doesn't leave the customer paying the old plan. (The per-workspace `PUT /admin/workspaces/:id/plan` was removed — the admin Workspaces list shows the plan read-only; grants happen in the Accounts view.) Promo codes live in `promo_codes` / `promo_redemptions`: **percent-off** codes create a Stripe **coupon + promotion code** (`src/main/admin/promo.js`) applied at Checkout; **free-plan** codes comp the plan on redemption (`src/main/billing/redeemPromo.js`, owner-only, **one per account** — checked across the account's workspaces by email) — like the admin grant, redemption **cancels any live account Stripe subscription** via `setAccountPlan` before comping. `planGuard.getPlanLimits` gates comped tenants correctly since they carry a paid (mirrored) `plan_name`.
- **Offers** (`offers` table, `src/main/admin/offers.js`, `src/common/offers.js`): an admin-set promotional **price** on a paid plan **for a billing interval** (`billing_interval` = `month`|`year`). One active offer per **(plan, interval)**; the baseline is that interval's list price via `listPrice(plan, interval)` (`plans.js`; monthly price, or the yearly TOTAL = `round(monthly×0.8)×12`), and `offer_price` is `DECIMAL(10,2)` so **fractional** offers are allowed. Backed by a Stripe **amount_off coupon** (`amount_off = (list − offer)` cents, `duration:'forever'`) so a fractional/yearly offer is charged **exactly** — not a rounded percent. Auto-applied at checkout for the **matching interval** when no promo code is passed (`createCheckoutSession` precedence: promo code → offer coupon → `allow_promotion_codes`). When a `promotionCode` **is** passed, `createCheckoutSession` first enforces the code's **`applies_to_plan`** scope (looks the `promo_codes` row up by `stripe_promotion_code_id`, rejects `400 promo_plan_mismatch` if the code is bound to a different plan) — the Stripe coupon behind a percent-off code has no product restriction, so this DB check is the only thing stopping a plan-scoped code from discounting another plan. `getActiveOffers` returns them nested **`{ [plan]: { month?, year? } }`** (with `interval`/`originalPrice`/`offerPrice`/`percentOff`); `getActiveOfferForPlanInterval(plan, interval)` is the checkout lookup. `getBillingStatus.offers` and the unauthenticated **`GET /public/offers`** (coupon id stripped) expose the nested map for the Billing tab / public pricing page. An offer is active only within its `[starts_at, ends_at]` window; date-only bounds are stored as LOCAL day boundaries (`… 00:00:00` / `… 23:59:59` strings) so timezone conversion doesn't shift activation. Deactivating an offer deletes its coupon.
- **Billing columns.** Source of truth is **`billing_accounts`** (keyed by `email`): `plan_name`, `stripe_customer_id`, `stripe_subscription_id`, `subscription_status`, `billing_interval` (`'month'|'year'`; NULL on free — surfaced by `getBillingStatus` as `billingInterval`), `current_period_end`, `pending_plan`/`pending_interval`/`pending_effective_at`. The same columns on **`tenants`** are a **denormalized mirror** of the OWNER's account (written only by `mirrorAccountToTenants`); tenant `stripe_*` ids are cleared/unused. **`tenants.plan_name` is never set by clients** (`updateTenant` doesn't accept it) — it only reflects the account plan.
- **Enforcement** via `src/common/planGuard.js` (`planAllows(tenantId, capability)`): `createIntegration` rejects with `402 PAYMENT_REQUIRED` + a `plan_limit_integrations` message on Free. **`deletePost`** requires the `owner` role (else `403 delete_feedback_owner_only`) **and** the `deleteFeedback` capability (Pro+, else `402 plan_limit_delete_feedback`) — the role check runs first. `seats` gates team invites. **`attachments`** (Pro+) gates feedback photo/video — see *Feedback attachments* below. **`contactSubmitter`** (Pro+) gates the submitter-contact feature: `getPostById` returns `author_email` as `null` on Free (so the email never reaches a Free client), and **`POST /posts/:id/notify-implemented`** (`notifyFeedbackImplemented`, owner-only) emails the submitter that their feedback is implemented — `402 plan_limit_contact_submitter` on Free, `400 feedback_not_completed` unless the post is `completed`, `400 no_submitter_email` if there's no address; on success it stamps `posts.implemented_notified_at`. **`multiDevice`** (Business only) governs one-device-at-a-time login — see *Device sessions* under Authentication.

### Feedback attachments

Photo/video on a feedback post, a **Pro+** capability (`limits.attachments`). Handlers in `src/main/attachments/attachments.js`; the guest-friendly `post_attachments` table (no uploader FK — public-board submitters have no account).

- **Two-step, upload-then-link.** A file is uploaded first (row with `post_id NULL`), then linked to the post it was submitted with. `storeAttachment(file, tenantId, lg)` validates kind + per-kind size and writes under `uploads/attachments/`; `attachToPost(db, ids, postId, tenantId)` claims only still-unlinked rows **in the same tenant** (an id can't be moved onto another workspace's post) and caps at `MAX_ATTACHMENTS_PER_POST` (3). `createPost` and `createPublicPost` accept `attachmentIds` and call it. Reads: `getAttachmentsForPost` on `getPostById` + `getPublicPostDetail`; board lists carry an `attachment_count` (+ a `thumbnail_path` on the public board).
- **Endpoints.** Authed dashboard: `POST /posts/attachment` (`authenticateToken` → `requireAttachmentsAuthed` → multer). Public board: `POST /public/:subdomain/attachments` (`attachPublicTenant` → `requireAttachmentsPublic` → multer). The plan gate (`src/middlewares/plan/requireAttachments.js`) runs **before multer** so a Free workspace never streams a rejected file (→ `402 plan_limit_attachments`). Field name is `file`; `src/common/file-upload/attachment-validator.js` allows images (png/jpg/webp/gif ≤10MB) + video (mp4/webm/mov ≤50MB, 50MB multer ceiling, 10MB image cap enforced in the handler).
- `resolvePublicTenant` exposes only `attachments_enabled` (a boolean from the plan), never the raw plan, so the portal knows whether to show the control. Attachments are served by the existing `/uploads` static mount; deleting a post cascades its `post_attachments` rows (FK `ON DELETE CASCADE`).
- Env: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_PRO`, `STRIPE_PRICE_BUSINESS`, `STRIPE_PRICE_PRO_YEARLY`, `STRIPE_PRICE_BUSINESS_YEARLY`. For local webhooks: `stripe listen --forward-to localhost:4560/webhooks/stripe`.

### Team invitations & email

- **Invite flow** (`src/main/invitations/invitations.js`, routes `src/routes/invitations/invitationRoute.js` at `/invitations` + two public routes on `/public`): the **owner** invites by email → a row in `invitations` with a `crypto.randomBytes(32)` **token**, a **7-day `expires_at`**, and `status='pending'`. The emailed link is `${FRONTEND_URL}/invite/<token>`.
- **Security.** The token is the credential. It is **single-use** — accept only matches `status='pending' AND expires_at > NOW()` (selected `FOR UPDATE` inside a transaction, so a double-click can't create two memberships) and then flips to `accepted`. Revoking sets `revoked`, killing the link instantly. Before sending, the address is checked for format **and a DNS MX lookup** (`isDeliverableEmail`) so typos like `gmial.com` are rejected; an inconclusive DNS result does not block.
- **Two accept paths.** *New user* → **public** `POST /public/invitations/:token/accept {fullName,password}` creates the account + membership (the link proves email ownership) and returns a JWT. *Existing account* → **authenticated** `POST /invitations/:token/accept`, which requires being signed in **as the invited email** (`invitation_wrong_account` otherwise) — otherwise anyone holding a forwarded link could join as that person.
- **Seats are now enforced** (the thing `plans.js` was waiting for): non-owner team members + outstanding invites must stay under `getPlanLimits(plan).seats`, else `402 plan_limit_seats`. `seats` counts members **besides the owner** (the owner, `role='owner'`, is excluded from the tally), so the effective totals are Free = owner + 2, Pro = owner + 5, Business = unlimited (∞ skips the check).
- **Per-account workspace caps** (`limits.ownWorkspaces` / `joinWorkspaces`) — how many workspaces one *account* (by email) may OWN and be a MEMBER of, distinct from the per-tenant `seats`. The account's **tier** is its subscription plan straight from `billing_accounts` (`getAccountTier(email)` in `planGuard.js`; a fresh/member-only account is `free`) — the account subscribes once and unlocks more workspaces. Free owns 1 / joins 1, Pro 3 / 3, Business unlimited. `getAccountWorkspaceUsage(email)` returns `{ tier, ownedCount, memberCount, ownLimit, joinLimit, canCreate, canJoin }` (limits `null` = unlimited) and drives: `createWorkspace` → `402 plan_limit_workspaces_own` when `!canCreate` (a first workspace is always allowed since owned=0), and `acceptInvitationAsExistingUser` → `402 plan_limit_workspaces_join` when `!canJoin`. `getWorkspaces` returns the same `limits` so the UI can gate "Add Workspace". (A brand-new invite acceptee owns 0 / is member of 0, so the join gate only bites existing accounts.)
- **One owner per workspace.** Invitees always join as `role='user'`. `updateUserRole` refuses to create a second owner (`workspace_already_has_owner`) or to demote the last one (`workspace_needs_an_owner`).
- **New-feedback notification.** When a visitor posts on a tenant's public board, `createPublicPost` calls `notifyOwnerOfNewPost` (`src/main/public/`) to email the workspace **owner** (template: `src/common/emails/newFeedbackEmail.js`, deep-links to `/dashboard/feedback/:id`). It is **fire-and-forget — deliberately not awaited** so a slow SMTP round-trip can't delay the visitor's submission, and it swallows its own errors so a mail failure can never fail the post. It skips notifying the owner about their own submission.
- **FeedBoard own feedback board (dogfooding).** `scripts/create-official-board.js [subdomain] [name]` (default `feedback` / `FeedBoard`) creates the workspace where users report bugs about **this app**. It is a normal tenant — no special-casing — owned by the platform admin **users** account (the `admins` row cannot own a workspace, so the script copies the existing `users` row for that email), comped to Business, with the standard three roadmap columns. Idempotent: re-running reuses the tenant and repairs a missing owner row or columns. The frontend links to it via `NEXT_PUBLIC_FEEDBACK_SUBDOMAIN`.
- **Brand icon = admin identity.** `src/common/brand-asset.js` (`ensureBrandAsset()`) copies the committed `assets/app-icon.svg` into the served tree at `uploads/branding/app-icon.svg` and returns that path. `scripts/set-official-branding.js` (idempotent) — and `create-official-board.js` on setup — store it as the platform admin's `users.avatar_url` (every row for the admin email → their profile picture everywhere) **and** the official board's `tenants.branding_logo_url`. So the admin's comments render the app icon as their avatar (the public reads return `author_avatar`) and the official board shows the app icon as its logo.
- **In-app activity notifications.** `src/common/notifications.js` (`notifyTeam`) fans a row into `notifications` for **every active team member** (owner + users) of a tenant, keyed per-user. Called fire-and-forget (not awaited, swallows its own errors) from `createPublicPost` (`new_feedback`) and `createPublicComment` (`comment_reply`), each with `reference_type='post'` + the post id so the client deep-links to `/dashboard/feedback/:id`. The actor (`excludeUserId`) — a logged-in member who posted/commented — is not notified of their own activity. This is what fills the dashboard Notifications page + header bell (`getUnreadCount`); nothing else creates notifications yet.
  - **Localization.** `title`/`message` are written **once, in English**, so they cannot be translated when a user whose UI is in another language later reads them. Pass **`meta`** (JSON column, added by `scripts/add-notification-meta.js`) with the structured pieces instead — e.g. `{ key: "comment", postTitle, who, body }` — and the frontend renders them via i18n in the *reader's* language. Keep writing `title`/`message` as the English fallback for rows predating the column. **Every new notification type must supply a `meta` shape** and matching frontend i18n keys, or it will be permanently English.
- **Mailer** (`src/common/mailer.js`): provider precedence **Resend HTTP API** (`RESEND_API_KEY`) → **SMTP/nodemailer** (`SMTP_HOST/PORT/USER/PASS`) → **dev logger** (no provider configured ⇒ the message + link are printed to the console so the flow stays testable). `sendEmail` never throws — a mail failure must not roll back the invitation. The branded HTML template lives in `src/common/emails/invitationEmail.js`.

### Account deletion

`src/main/users/deleteAccount.js` (`POST /users/account/deletion-summary` + `POST /users/account/delete`, both authenticated). An account is an **email** with one `users` row per workspace, so deleting it means:

- **Re-authentication.** The current password is bcrypt-verified first — a hijacked session must not be able to destroy the account.
- **Owned workspaces are deleted outright** (one owner per workspace, no ownership transfer ⇒ they can't be orphaned). Any Stripe subscription is **cancelled first** so billing stops. `DELETE FROM tenants` then cascades everything (verified: the cascade succeeds even though some child FKs are `RESTRICT`, because those rows are cascade-deleted too).
- **Joined workspaces keep their data** — only the membership row goes. But several FKs into `users` are **`ON DELETE RESTRICT`**, so a plain delete would fail. Content that belongs to the *workspace*, not the leaver, is preserved instead of destroyed:
  - `posts.author_id` / `comments.author_id` (nullable) → **set NULL** (they stay on the board, shown as Anonymous).
  - `changelog_entries.created_by`, `api_keys.created_by`, `file_uploads.uploaded_by` (NOT NULL + RESTRICT) → **reassigned to that workspace's owner**.
  - `votes` / `notifications` / `oauth_accounts` cascade away; `audit_logs.actor_user_id` is `SET NULL`.
- All of it runs in one transaction, and pending `invitations` addressed to the email are cleaned up.

**If you add a new table referencing `users(id)`**, decide its delete rule deliberately — a `RESTRICT` + `NOT NULL` column must be handled in `deleteAccount` or account deletion will start failing.

### Conventions & gotchas

- **`paginationData` middleware REBUILDS `req.body.paginationData`** from a fixed set of fields (`itemsPerPage`, `currentPageNumber`, `sortOrder`, `filterBy`, `offset`, `sortBy`). Anything else you put in it is **silently dropped before the handler sees it** — if you add a new pagination field, whitelist it there too or you'll get a baffling "the handler works when called directly but not over HTTP" bug.
- **Board sort** (`newest` | `oldest` | `most_voted` | `least_voted`) is a `SORTS` map in both `getPostList.js` (dashboard) and `getPublicBoard.js` (portal); both order by `p.is_pinned DESC` first, then the chosen sort. `vote_count` is a SELECT alias, so the vote sorts work without a join.

- **Bodyless requests:** a global middleware in `app.js` defaults `req.body` to `{}`. Without it, GET/DELETE routes that read `req.body.lg` (or any body field) crash with `Cannot read properties of undefined`. Keep that middleware, and prefer `req.body?.x` in handlers.
- **Partial updates:** `UPDATE` handlers should set only the columns actually provided (build the `SET` clause dynamically). A blanket `SET col = ?` with an `undefined` value silently nulls existing data — e.g. moving a roadmap item must not wipe its `target_release_date`.

### File uploads

- `multer` handles multipart; `sharp` optimizes/resizes images
- Max size set via `FILE_UPLOAD_MAX_SIZE` env var (default 10MB)
- Files stored under `./uploads/` with unique names
- `checkIfFileSavePathExist` middleware creates the directory if missing
- **`POST /uploader/upload-image` is a GENERIC uploader** (`insertImageData`): it only stores the file and returns its path. It must **not** mutate the user's `avatar_url` — the same endpoint uploads the profile avatar *and* the Branding company logo, so writing the avatar there would leak the logo into the uploader's profile photo. The avatar is set only by the profile save (`updateUserData` with `avatarUrl`); the logo is saved as the tenant's `branding_logo_url`.

### Resilience & abuse protection

The public API is unauthenticated and internet-facing, so these are load-bearing — **do not remove them to "simplify" a route**.

- **Rate limiting** (`src/middlewares/security/rateLimiters.js`), four tiers, all env-tunable:
  - `apiLimiter` — global net, 300/min/IP, mounted before body parsing so a flood is rejected before we spend CPU parsing it.
  - `authLimiter` — 10 **failures**/15min on `/users/login`, `/users/register`, `/admin/auth/login`. `skipSuccessfulRequests` means normal users are never locked out. Each attempt costs a ~100ms bcrypt hash, so this is a CPU-exhaustion control as much as an account-security one.
  - `publicWriteLimiter` — 15/min on the guest-writable portal routes (feedback, comments, votes, attachments). Keyed by **IP + tenant** so flooding one board can't exhaust the budget for other tenants behind the same NAT. Uses `ipKeyGenerator` (IPv6 /64 normalization) — a raw `req.ip` key lets one IPv6 host rotate addresses within its own prefix.
  - `expensiveActionLimiter` — 30/hr on email/Stripe fan-out (`/invitations`, `/billing/checkout`).
  - **Counters are per-process.** Under cluster mode the aggregate ceiling is workers × max. Still a hard bound; use `rate-limit-redis` if exact global limits are ever needed.
- **`trust proxy` = 1 hop.** Behind a proxy every client would otherwise share one bucket. Trusting *all* hops is worse — a client could forge `X-Forwarded-For` and bypass limiting entirely.
- **Timeouts** (slowloris): `server.requestTimeout` 30s, `headersTimeout` 20s, `keepAliveTimeout` 15s, `maxConnections` 2000, plus a per-request `res.setTimeout` → 503.
- **Pagination is capped, twice.** `paginationData` clamps to `MAX_ITEMS_PER_PAGE` (100); `getPublicBoard` clamps independently to 50 **because the public board does not go through that middleware**. Uncapped, one request (`itemsPerPage: 1000000`) buffers millions of rows and OOMs the process.
- **Crash guards** (`app.js`): `unhandledRejection` logs and keeps serving (one forgotten `.catch()` on a background email shouldn't kill a healthy server); `uncaughtException` shuts down cleanly for PM2 to restart (state is undefined — don't keep serving).
- **Graceful shutdown** drains the DB pool and flushes logs. Skipping the drain leaves MySQL holding sockets; across repeated restarts that exhausts `max_connections`.
- **Cluster mode** (`ecosystem.config.js`): `exec_mode: "cluster"`, `instances: "max"` (`PM2_INSTANCES` to pin). Node is single-threaded — fork mode used one core regardless of machine size. Measured ~54% more throughput on 2 workers. `kill_timeout: 20000` must stay above `SHUTDOWN_TIMEOUT_MS`.

### Performance

- **Caching** (`src/common/cache.js`): in-process TTL Map, capped at `CACHE_MAX_ENTRIES` (unbounded caches are their own memory leak). Deliberately **not Redis** — no such infra in this deployment, and a Map removes the round-trip entirely. The API mirrors a Redis client so swapping is a one-file change. Applied to `resolvePublicTenant`, the single hottest query (every portal request resolves the tenant first). **TTL is 10s on purpose:** explicit invalidation only reaches the worker that handled the write, so under cluster mode TTL — not invalidation — bounds staleness. 10s already collapses >99.9% of lookups under a burst; longer buys almost nothing and makes a stale logo linger. **Call `invalidateTenantCache(oldSub, newSub)` on any write that changes what the portal reads** (branding, name, subdomain, active, plan).
- **N+1:** `getPublicBoard` previously ran **four correlated subqueries per row** (votes/comments/attachments/thumbnail) — and the `most_voted` sort forced them over *every* matching row before `LIMIT`. Now: one pre-aggregated derived table for `vote_count` (the sort needs it inline) plus three batched lookups over the page's ids, run concurrently. Query count is constant regardless of page size. Measured: **~22–25% faster at 500–2000 posts, ~20% slower below ~100** (four round-trips beat one when the subqueries are trivially cheap) — the trade is deliberate, since small boards are sub-millisecond either way.
- **Compression:** `compression()` gzips all compressible responses (JSON/text); binary `/uploads` are skipped by its content-type filter.
- **Async logging** (`src/common/logger.js`): morgan writes to a **buffered `fs.WriteStream`**, not stdout. Under PM2 stdout is a pipe, which Node writes **synchronously** — every log line blocks the event loop. Production also skips 2xx/3xx unless slower than `SLOW_REQUEST_MS`; logging every 200 OK is what fills a disk during an attack, and a full disk is a crash.
- **Body parsing:** `express.json({ limit: "1mb" })` (was 10mb). Real bulk goes through multer on the upload routes and never touches this parser; 10mb just meant a few concurrent requests could pin hundreds of MB of heap. `parameterLimit` 1000 (was 10000 — enough for a CPU-burn payload).
- **Connection pool** (`database/dbPool.js`): keep-alive enabled (prevents random `ECONNRESET`), idle recycling (`maxIdle`/`idleTimeout`), `connectTimeout`. Size via `DB_CONNECTION_LIMIT` / `DB_MAX_IDLE` env (default 15 / 10).
- **Static assets:** `/uploads` served with `Cache-Control: public, max-age=7d, immutable` (upload filenames are timestamped, so caching is safe).
- **Error handling:** a JSON 404 + central error handler are the last middlewares in `app.js` — unhandled errors return `{ status, message }`, never an HTML stack trace.
- **Indexes:** the schema is already well-indexed (composite `tenant_id`+column keys, FK indexes). Profile with `EXPLAIN` before adding more — every index slows writes.

### Database schema (25 tables)

Core: `tenants`, `users` (role `owner`/`user`), `invitations`, `posts`, `post_attachments` (photo/video, Pro+), `votes`, `comments`, `tags`, `post_tags`
Features: `roadmap_columns`, `roadmap_items`, `changelog_entries`, `notifications`
System: `api_keys`, `audit_logs`, `integrations`, `oauth_accounts`, `user_sessions` (device sessions — see Authentication), `password_resets` (forgot-password tokens — see Authentication)
Platform (not tenant-scoped): `admins`, `promo_codes`, `promo_redemptions`, `offers`, `support_sessions`, `support_messages` (support chat — see Support chat)

Post fields of note: `type` (feedback/feature/bug), `status` (`open`/`planned`/`in_progress`/`completed`/`closed`/`rejected`), `priority` (1–5). **`rejected`** = feedback the team declined: `updatePostStatus` validates the value; on the dashboard it appears in the "All" tab and its own "Rejected" tab (`getPostList` applies no special exclusion); the **public** board (`getPublicBoard`) and post detail (`getPublicPostDetail`) exclude it unconditionally so it's never shown to end users. It's restored by setting status back to `open`. (`closed` is a legacy value, not offered in the UI.)
